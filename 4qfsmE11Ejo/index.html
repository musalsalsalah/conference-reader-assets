Monolith Terminology

The term 'monolith' comes from Greek 'monolithos,' meaning one stone. It describes a single block of stone, often used as a monument. In software, it incorrectly implies indivisibility, causing confusion.

  • Monolith was historically used to describe a big chunk of code, not a specific architectural approach. The term was misapplied to software architecture.
  • The Oxford English Dictionary defines monolith as a large structure, but this was misapplied to software to imply indivisibility.
  • The speaker noted that monoliths often have packages and subsystems, contradicting the assumption they are unorganized.

Defining Microservices

Microservices are an architectural style where a single application runs as small, independent services. Each service runs in its own process and communicates via lightweight mechanisms.

  • Services are built around business capabilities, not technical domains, aligning development with organizational goals.
  • Services must be independently deployable using CI/CD pipelines, enabling continuous delivery.
  • Microservices require clear interfaces with contractual semantics, not just syntax, to avoid implementation leakage.
  • Each service hides its internal design decisions, promoting stability and independent evolution.

Modular Monoliths: A Misunderstood Concept

The term 'modular monolith' emerged from a misunderstanding of software architecture. It describes a monolith structured into modules using rational criteria, not a negative term. Simon Brown coined it in 2015 to clarify that microservices don't inherently provide more modularity than well-structured monoliths.

  • Modular monoliths use information hiding to minimize internal knowledge exposure. Interfaces reveal only necessary details about inner workings.
  • This approach aligns with Alan Kay's object-oriented philosophy, not Dave Parnas' 1972 principles.
  • Microservices replicate decades-old modularity principles with added runtime and deployment complexity.

Origins of Modularity Principles

Modularity principles trace back to 1968 and earlier. The 1968 NATO conference on software engineering introduced key ideas, though the term 'software engineering' was coined by Margaret Hamilton in the mid-1960s for Apollo guidance systems.

  • Dave Parnas' 1972 paper defined information hiding: modules hide design decisions behind minimal interfaces.
  • Butler Lampson's 1983 work described interfaces as contracts between clients and suppliers in component-based development.
  • Smalltalk 80 (1980) influenced modern paradigms like agile, XP, and test-driven development through its uniform object model.

Object-Oriented Programming Misconceptions

Alan Kay's object-oriented philosophy is often misunderstood. It emphasizes messaging, local state protection, and extreme late binding—not auto-properties or dependency-injected 'manager' classes.

  • True object orientation avoids 'anemic domain models' and manager objects. These are common but incorrect implementations.
  • Smalltalk 72 (1972) and Smalltalk 80 (1980) pioneered these ideas. Ruby retains Smalltalk's influence, while Objective-C combines C and Smalltalk poorly.
  • The Unix philosophy ('write programs that do one thing well') predates and parallels these concepts.

The Microservices Misstep

Microservices were mistakenly seen as an unconditional good. They replicate modularity principles but add runtime complexity. The term 'modular monolith' clarifies that modularity exists in well-structured monoliths.

  • Microservices don't provide more modularity than a modular monolith. They offer different trade-offs in deployment and runtime.
  • Early modularization happened due to technical limits like editor memory or compiler constraints, not architectural choice.
  • Alan Perlis observed that all programs eventually become 'raccoon'—overly complex and fragile—regardless of architecture.

Modularity: Not Just a Buzzword

Modularity is a stable principle, not a new trend. It applies across development, deployment, and runtime stages. The term's meaning shifts depending on context, causing confusion.

  • Modular design dates back to the 1960s, with principles like clean separation of concerns and well-defined interfaces remaining relevant today.
  • Development modularity involves source code organization, while deployment modularity refers to deployable units like Java modules or OSGi bundles.
  • Runtime modularity describes how processes or memory structures appear during execution, such as separate processes in microservices.

The Real Problem: Messy Architecture

The issue isn't monoliths versus microservices—it's messy architecture. Both can be poorly structured, but microservices add complexity without benefits.

  • A well-structured monolith can outperform a poorly structured microservices system in maintainability and deployment speed.
  • Microservices amplify existing problems, making them harder to fix due to added complexity and communication overhead.
  • Fault tolerance matters most in critical systems like Mars rovers, where crashes cost hundreds of millions of dollars.

Architectural Principles Across Time

Architectural principles like modularity remain stable despite changing technologies. Surface-level tech changes rapidly, but core principles endure.

  • Mars Curiosity's codebase used C99 with static analysis and VxWorks, emphasizing clean separation of concerns and fault tolerance. The speaker noted the landing year as 'around 2012' with uncertainty.
  • Fault tolerance is critical for space systems but less so for mobile apps, where crashes are merely annoying.
  • Programming languages often outlive their users, showing how some tech layers change slowly compared to surface innovations.

Defining Architecture Clearly

Architecture should answer three questions: What are the structural elements? How do they interact? What constraints apply? This avoids ambiguous terms like 'module.'

  • Structural elements include functions, development modules, and runtime processes, each at different scales of system design.
  • Avoiding terms like 'module' prevents confusion, as their meaning varies across contexts and eras.
  • Paul Dyson and Andy Long's book offers a clear framework for defining architecture through these three questions.

Architectural Elements and Relationships

When sketching a system on a whiteboard, focus on structural elements and their relationships. Whiteboards help clarify collaboration and avoid missing key details. Many conferences lack whiteboard budgets, but they're essential for visualizing architecture.

  • Relationships include HTTPS connections, object references, class inheritance, and API implementations.
  • A module can mean any structural element, but naming is hard due to inconsistent terminology like 'component' or 'package'.
  • Java's package is a namespace with many leaks, not a delivery unit or module, causing confusion.

Naming Challenges in Software

Naming is hard because it requires precise meaning. Terms like 'module', 'component', and 'package' often overlap or conflict, leading to miscommunication.

  • A 'component' might mean a runtime deployable unit or just a part of a composition, such as a class or function.
  • Services now offer services, and 'process' can refer to OS processes or runtime isolation units, causing ambiguity.
  • Avoid 'non-functional requirements'—it means broken. Instead, specify what you need, like performance or maintainability.

Functional vs. Operational Trade-offs

Separate requirements into functional (semantics) and operational (runtime qualities). Developmental aspects like maintainability are also key.

  • Functional requirements are verified via unit tests; operational focuses on qualities like performance and availability.
  • Trade-offs involve balancing runtime needs against development complexity. Better performance may increase code complexity.
  • Microservices don't guarantee benefits; they can worsen performance or development complexity without careful consideration.

Timeless Architectural Considerations

Modular monoliths use 1970s structured programming principles. History shows many modern ideas are revisited, not invented.

  • The 1972 book on structured programming remains relevant, highlighting that some concepts are deeply rooted in history.
  • Architectural choices require context-aware trade-offs, not simple assumptions like 'more complexity = better performance'.
  • Avoid binary thinking: functional vs. non-functional is misleading. Focus on what the system actually does and how it runs.

Modular Boundaries Define Systems

Modular boundaries matter more than monoliths. They exist at multiple levels: code (function, class, module), deployment, team structure, and runtime. Boundaries define trust and relationships between components.

  • Boundaries differ in purpose. A house door lock prevents outside entry, while a bathroom lock protects privacy. Similarly, module boundaries serve different roles based on context.
  • Team structure aligns with module ownership. Conway's Law (1968) shows teams mirror system boundaries. This applies to microservices and team topologies.
  • High coupling means modules depend on each other. Changes in one module often break others. Minimize coupling but don't eliminate it—systems need some interdependence.

Cohesion and Comprehensibility

Cohesion measures how well elements within a module work together. High cohesion means a module is a single, integral unit. This differs from the misunderstood single responsibility principle.

  • Comprehensibility requires studying systems one module at a time. Teams with 100k lines of code had similar functionality to teams with 1M lines but better outcomes.
  • High cohesion reduces cognitive load. A module should feel like 'one thing,' not a collection of responsibilities.
  • AI tools struggle with large codebases. Smaller modules improve developer and AI efficiency.

Historical Context and Modern Relevance

Modular programming ideas date back to 1970s works like Dijkstra's separation of concerns and Parnas' information hiding. These concepts remain relevant today.

  • Parnas (1972) listed benefits: shorter development time, product flexibility, and comprehensibility. These mirror modern microservices goals.
  • Information hiding (Parnas 1971) defines module connections as shared assumptions. Dependencies often exist beyond code, like JSON or database conventions.
  • Systems with high coupling appear tangled. Clear separation improves understandability and reduces maintenance pain.

Trade-offs and No Silver Bullets

Modularity requires balancing trade-offs. Runtime needs, deployment strategies, and team structure influence boundary decisions. There's no single solution.

  • Teams with 100k lines of code outperformed those with 1M lines in functionality, reliability, and developer satisfaction.
  • Full-stack knowledge is often misunderstood. True full-stack means understanding modular relationships, not just JavaScript and databases.
  • Software development cycles repeat ideas. New terms like 'microservices' build on old concepts without replacing them.
