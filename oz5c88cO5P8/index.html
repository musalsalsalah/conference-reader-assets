System Design Interview Basics

System design interviews test your ability to build scalable systems under pressure. They're intense because you must consider multiple components and trade-offs. The goal is to provide a framework for answering questions, not to memorize specific technologies.

  • Interviewers don't expect perfect systems in 45 minutes. They value clear communication and problem-solving over technical specifics.
  • Common failures include jumping straight to architecture without clarifying requirements or over-engineering with unnecessary components.
  • Successful candidates ask targeted questions to define the problem before designing.

What Interviewers Really Want

Interviewers focus on four key skills: judgment under ambiguity, technical depth, communication, and collaboration. They assess how you handle vague problems and explain trade-offs.

  • Good candidates narrow vague problems into concrete requirements. Bad candidates draw complex diagrams without clarifying scope.
  • Example: One candidate focused on Instagram's photo feed and follow system; another wasted time on search and messaging features.
  • Interviewers reject candidates who ignore interviewer-provided numbers like '10,000 users' and build over-engineered systems.

The Six-Step Framework

Follow this six-step method to structure your system design answers. It ensures you address requirements before building solutions.

  • Step 1: Clarify requirements. Spend 5 minutes making the problem concrete. Example: Define Instagram as photo posting, following, and fast feed loading.
  • Step 2: Back-of-envelope estimation. Estimate user numbers and usage patterns. Example: 10 million daily users, read-heavy (100 scrolls/week vs. 1 post/week).
  • Step 3: Define API. Identify key user actions: upload photo, follow user, get home feed. These define what the system must store.
  • Step 4: High-level design. Draw basic components: user, app server, databases for users/follows, photo storage, and data flow.
  • Step 5: Deep dives. Focus on hard parts like Instagram's home feed algorithm for million-follower posts.
  • Step 6: Bottlenecks and scaling. Analyze weak points (e.g., follows database bottleneck) and propose fixes like adding cache.

Clarifying Requirements

The first 5 minutes are critical. Ask targeted questions to define scope. Avoid memorized questions that don't impact your design.

  • Bad question: 'Should I use SQL or NoSQL?' Database choice depends on data needs, not interviewer input.
  • Bad question: 'Should the system be scalable?' Scalability is assumed; ask for user numbers instead.
  • Good questions focus on functional and non-functional requirements: user count, read/write ratio, data loss tolerance, and latency needs.
  • Example: For a photo-sharing app, ask 'How many users and how fast are they growing?' and 'Do people scroll more than post?'

Clarify Requirements First

Ask questions that change the design. For URL shorteners, focus on custom links, expiration, and analytics. Answers define scope and features.

  • Custom links are disallowed. Short links never expire. Analytics are optional but not required.
  • Clarify scope: create short links that redirect to original URLs without custom options or expiration.

Estimate System Scale

Estimate numbers that impact design. Focus on daily link creation, click volume, and total storage needs.

  • 1 million new links per day equals 12 per second. Databases handle this easily.
  • Each link gets 1,000 clicks on average. This makes reads 1,000x more frequent than writes.
  • Over 10 years, store 3.6 billion links. Focus on optimizing read performance for high traffic.

Design the Core API

Define two essential APIs: create short link and redirect to original URL. This requires a simple key-value mapping.

  • Two essential APIs: create short link and redirect to original URL.
  • Store a simple key-value mapping: short code to long URL in a database.
  • Use Postgres with an index on short codes. Avoid NoSQL for this simple key-value need.

Generate Unique Short Codes

Choose between hashing and counting. Hashing risks collisions. Counting avoids collisions but requires shuffling for security.

  • Hashing may require retries. Check database for existing codes after generating a hash and retry if needed.
  • Counting with a global counter avoids collisions. Encode numbers in base 62 for short codes.
  • Base 62 uses 62 characters (0-9, a-z, A-Z). Seven characters provide trillions of unique codes.

Address Security and Concurrency

Shuffle counter numbers before encoding to prevent guessing. Handle concurrent requests with atomic operations.

  • Shuffle counter numbers before encoding to prevent guessing. Apply fixed secret rules.
  • Counter collisions occur if two requests access simultaneously. Use atomic operations to prevent this.
  • Shuffling maintains uniqueness while making codes appear random to attackers.

Handling High Traffic with Caching

Normal traffic: 1 billion daily redirects, about 11,000 database reads per second. A viral link can cause 1 million clicks in an hour, overwhelming a single database.

  • Database reads for the same URL are wasteful since the answer never changes.
  • A celebrity link can generate 1 million clicks in an hour, causing a traffic spike.
  • 11,000 reads per second is already a lot for one database machine.

Cache Implementation

Use Redis cache to store hotkeys (popular links) for faster access. The cache serves the same URL mapping without database queries.

  • First cache hit: database read, then cache stores the URL for future requests.
  • Caching works perfectly for URL shorteners since mappings never change.
  • Redis answers in under a millisecond, making it ideal for this use case.

Cache Staleness and Limitations

Cache memory is limited; Redis removes unused entries to make room for new ones. Popular links stay cached while inactive links are removed.

  • Cache staleness is not a problem because URL mappings are permanent and never updated.
  • Redis automatically removes unused entries, keeping the cache efficient.
  • This is a dream case for caching since the data never changes.

Advanced Caching Strategies

For extremely hot links, store top links in each server's memory. Use a CDN to serve links from servers closest to the user.

  • Each application server can keep its own small copy of the top links in memory.
  • CDN serves users from the nearest server, reducing latency for global users.
  • CDN ensures Tokyo users get URLs from nearby servers, not Virginia.

Redirect Type Selection

Choose 302 redirects over 301 to keep analytics and control. 301 redirects cause browsers to remember the destination, skipping future requests.

  • 302 redirects keep every click flowing through the service for analytics.
  • 301 prevents tracking clicks and makes disabling links impossible.
  • 302 allows disabling links if they point to scam pages.

System Resilience and Data Safety

Cache failure slows the system but doesn't break it. Database handles all reads during cache downtime.

  • Database must have replicas and backups to prevent data loss from the mapping table.
  • Global counter must never repeat numbers to avoid duplicate short codes.
  • Cache is a performance layer, not the source of truth.

Follow-Up Questions and Solutions

Follow-up questions test design changes. Two requests at once need locks. Counter as single point of failure requires blocks of numbers.

  • Two requests at once: Use locks to ensure only one request accesses the counter.
  • Counter as single point of failure: Servers request blocks of numbers at once.
  • Link expiration: Add expiry dates to the mapping table and check before redirecting.

Rate Limiter Design

Rate limiters prevent abuse in systems like ChatGPT and URL shorteners. Without them, a user named Shadow could flood APIs with 1 million requests per hour, filling databases with junk URLs and slowing legitimate users.

  • Reject requests exceeding 100 per minute per user. Respond with HTTP 429 and a retry-after header.
  • Track requests by account for logged-in users. Track by IP address for non-logged-in users.
  • Normal users make about 100 requests per day. Heavy users hit the 100-per-minute limit.

Clarifying Requirements

Ask three key questions before designing: how to identify users, what limit to set, and how to handle exceeded limits. Each choice has trade-offs.

  • Tracking by IP blocks entire offices sharing a connection. Attackers can change IPs to bypass limits.
  • Tracking by API key only works for developers. Most users don't use API keys.
  • Reject requests exceeding limits immediately. Include retry-after headers to prevent retry loops.

Back-of-the-Envelope Estimation

Estimate storage and request rates to guide design. A simple counter uses 50 bytes per user, fitting 10 million users in 500 MB.

  • 10 million users make 1 billion requests daily. Peak traffic reaches 35,000 requests per second.
  • Normal users make about 100 requests per day. Heavy users hit the 100-per-minute limit.
  • Fixed window limits allow 200 requests in 2 seconds. Sliding window tracks exact timestamps for last 60 seconds.

High-Level Design

Place the rate limiter at the API gateway to reject requests early. Start with a simple fixed window, then address its flaws.

  • Fixed window resets counters every minute. Allows 200 requests in 2 seconds during minute transitions.
  • Sliding window logs every request timestamp. Uses 2.5 KB per user, totaling 25 GB for 10 million users.
  • Token bucket holds 100 tokens per user. Fills at 1.67 tokens per second, allowing bursts.

Token Bucket Rate Limiting

The token bucket algorithm provides a sustained rate of 1.67 tokens per second. This approach differs from fixed windows by allowing intentional burst control. A smaller bucket size reduces burst allowance without changing the sustained rate.

  • Bucket size determines burst allowance. A 20-token bucket allows 20 requests at once while maintaining 1.67 tokens per second.
  • Each user's bucket stores only tokens remaining and last refill time. This requires just 50 bytes of memory per user.
  • Users can spend all 100 tokens in one go if the bucket is full. They still get two requests per second when the bucket is empty.

Distributed System Challenges

Multiple API gateways cause inconsistent rate limiting. Each gateway tracks separate buckets for the same user, effectively doubling available requests.

  • Moving buckets to shared storage like Redis solves the problem. All gateways access the same bucket data.
  • Atomic operations prevent race conditions. Redis executes read-modify-write as a single script.
  • Without atomic operations, two gateways could both allow a request when only one token remained.

Performance and Failure Modes

Redis handles 100,000 operations per second. Our system needs 35,000 operations per second, leaving room for growth. Network latency affects performance significantly.

  • 1ms latency is acceptable if Redis is in the same region. 50ms latency makes the rate limiter the system bottleneck.
  • Fail open allows all requests during Redis failure. This is safer for normal APIs like Stripe's.
  • Fail closed blocks all requests during Redis failure. This is safer for sensitive endpoints like login APIs.

Customizable Rate Limits

Different APIs require different rate limits. Limits depend on API functionality and resource usage.

  • Read APIs can handle 10,000 requests per minute. Create APIs are limited to 100 requests per minute.
  • Login APIs have the strictest limits. Three consecutive calls may trigger rate limiting.
  • Rate limits are stored as rules. The gateway applies the correct rule based on the API endpoint.

Scaling Redis for High Traffic

One Redis instance handles 100,000 operations per second. For 1 million requests per second, we need about 10 Redis instances.

  • Redis instances can be partitioned by user. All requests for a user go to the same Redis instance.
  • Partitioning prevents cross-instance communication. Each Redis instance manages its own user buckets.
  • High traffic users may still trigger rate limits. The system handles this by maintaining consistent user bucket access.

Rate Limiter Optimization

Current rate limiting checks every API request against Reddus, causing high load even at low limits. For example, 50,000 requests per second would trigger 50,000 Reddus calls.

  • Stripe uses a local counter in API gateway memory that syncs with Reddus every few hundred milliseconds.
  • This avoids network calls to Reddus on every request, reducing load significantly.
  • The gateway rejects requests immediately once it knows a user is blocked, avoiding Reddus checks.

Notification System Requirements

Notification systems deliver event-based messages to users across channels like push, SMS, email, and in-app dots. They must respect user preferences and handle two notification types differently.

  • Transactional notifications (e.g., payment confirmations) require near-instant delivery within seconds.
  • Marketing notifications (e.g., flash sales) can tolerate delays of a few seconds.
  • Losing notifications is bad, but duplicate notifications are worse (e.g., double payment SMS).

System Design Framework

Clarify requirements before designing. Key questions include notification types, delivery channels, speed requirements, and tolerance for lost/duplicate messages.

  • Ask if users can disable marketing notifications but not transactional ones.
  • Determine if notifications must be delivered instantly or can be queued for later processing.
  • Confirm whether losing notifications or sending duplicates is more critical to avoid.

Notification Delivery Mechanics

The system stores notifications in a database with fields like user ID, channels, message body, and status. External services handle actual delivery.

  • Push notifications use APNS (Apple) or FCM (Google) gateways. SMS uses providers like Twilio.
  • Emails go through services like SendGrid. These external systems can fail or delay delivery.
  • In-app notifications track if users have seen messages; SMS/email lack read receipts.

Notification Storage and Preferences

Store notifications in a SQL database like PostgreSQL. Each notification is a small row. Even 10 million notifications daily (100 writes per second) is manageable. Also store user preferences to determine if marketing notifications can be sent.

  • Use PostgreSQL for storage. It handles small rows efficiently. 100 writes per second is well within capacity.
  • Store user preferences separately. This determines if marketing notifications are allowed for each user.
  • Database holds full notification details: message body, channels, status, timestamp.

Initial Notification Flow

The notification server saves requests to the database with status 'pending'. It then sends notifications directly to providers. This approach fails under high load or crashes.

  • Server waits for confirmation from all providers. This causes 1-2 second delays per notification.
  • A server crash during processing can lose notifications. For example, if a notification is partially sent but confirmation is missing.
  • This method works for small scale but not for high traffic or failures.

Queue-Based Processing

Use a queue to separate notification acceptance from sending. The database holds full records. The queue holds small tickets with notification IDs and a note that the notification is waiting to be sent.

  • Queue holds notification IDs and a note that the notification is waiting to be sent.
  • Workers pick tickets from the queue. They fetch full details from the database and send to providers.
  • If a worker crashes, the queue reassigns the ticket to another worker. No data loss occurs.
  • Multiple workers can run in parallel. This eliminates single points of failure.

Queue Requirements

Choose a queue with three key properties: durability, acknowledgment, and multi-worker support.

  • Durable: Store tickets on disk, not RAM. Prevents data loss if the queue restarts.
  • Acknowledgment: Remove messages only after workers confirm completion.
  • Multi-worker: Support adding more workers as queue size grows.
  • No strict ordering needed. Notifications can be processed out of order without issues.

Channel-Specific Queues

Use separate queues for each notification channel. This prevents one slow provider from blocking all channels.

  • Email provider slowdown only affects email notifications. Other channels continue processing.
  • In-app notifications require no external providers. Workers mark them as sent directly in the database.
  • In-app notifications use a 'seen' flag. The mobile app checks this flag when displaying notifications.
  • Fan-out distributes one notification event to four separate queues for each channel.

Handling Provider Failures

When a provider fails, retry politely. Avoid overwhelming the provider with immediate retries.

  • Retry with increasing delays: 1 second, then 2 seconds, then exponential backoff.
  • Do not retry immediately. This prevents overloading the provider during outages.
  • Example: If email provider is down for 30 minutes, workers retry with delays to avoid API overload.

Exponential Backoff for Retries

Retry with increasing delays after failures. Wait 4 seconds before the first retry, then double the wait time each time. Stop retrying after several attempts.

  • Wait 4 seconds before the first retry, then double the wait time for each subsequent retry.
  • Move failed notifications to a dead letter queue after several unsuccessful attempts.
  • This prevents overwhelming slow email providers during repeated failures.

Handling Duplicate Notifications

Workers may crash after sending a notification but before acknowledging the queue. This causes duplicate processing. Use a shared store to track sent notifications.

  • Check the shared store before sending to avoid duplicates.
  • The shared store uses a notification ID as a potency key with an expiry time.
  • If the worker crashes after writing the ID but before sending, the notification is not sent but the ID remains.

Potency Key Mechanism

Before sending, check if the notification ID exists in the shared store. If it does, drop the ticket. If not, write the ID with an expiry before sending.

  • Write the ID to the shared store before calling the provider.
  • The ID expires after one minute to allow retries if the notification wasn't sent.
  • This ensures duplicates are harmless. The system tolerates duplicates but prevents them from being sent.

Queue and Worker Flow

Notifications are saved in the database with a unique ID and pending status. A background job adds pending notifications to the queue to avoid two separate writes.

  • Save notifications in the database first with pending status.
  • The background job processes pending notifications and adds them to the queue.
  • Each channel has its own queue to prevent slow providers from blocking others.

Failure Handling and Scaling

Retry failed notifications with exponential backoff. Move persistent failures to a dead letter queue. Add more workers if queues grow too large.

  • Retry with exponential backoff for temporary failures.
  • Move notifications to a dead letter queue after several failed attempts.
  • Add more workers to process larger queues during high traffic.

At-Least-Once Delivery

The system uses at-least-once delivery. It may send duplicates but ensures no notifications are lost. Potency keys make duplicates harmless before the provider call.

  • Exactly once delivery is impossible in distributed systems.
  • Potency keys ensure duplicates are dropped before the provider call.
  • The worst case is a notification sent slightly late, not duplicated.

Real-World Notification Systems

LinkedIn and Uber use centralized notification platforms. LinkedIn's Air Traffic Controller handles all notification types through a single gateway, reducing email volume by 50% and complaints by over 65%.

  • LinkedIn replaced multiple team-specific notification systems with Air Traffic Controller, eliminating duplicate notifications across all channels.
  • Uber uses priority buckets for push notifications, sending trip updates before promotional offers.
  • Priority buckets ensure transactional notifications like login codes reach users within seconds.

Handling Notification Queue Issues

Interviewers test design adjustments with follow-up questions. Key scenarios include queue management and system failures.

  • Marketing campaigns should not block transactional notifications. Separate queues prevent login codes from being delayed.
  • Email provider downtime requires durable queues and circuit breakers. Workers retry until the provider recovers.
  • Backup email providers ensure continuity during outages. Login codes are only valid for about a minute, so late delivery is useless.

Exactly Once Delivery Challenges

Exactly once delivery is impossible due to network uncertainties. Systems use item potency keys to avoid duplicates.

  • A worker may time out after sending a notification. The system cannot confirm if the message was delivered.
  • SMS providers accept item potency keys. Duplicate messages are blocked using unique notification IDs.
  • Even with mechanisms, edge cases like network issues can cause duplicate notifications.

News Feed Design Fundamentals

A news feed shows posts from followed accounts in chronological order. It is not a news app but a social media feed.

  • LinkedIn and X display feeds of posts from followed users. The feed is an endless scroll of recent content.
  • Feed requirements include sorting by timestamp, loading within one second, and supporting text, images, and videos.
  • Duplicate posts after refresh are acceptable. New posts appear within seconds for followers.

Scalability Considerations

News feeds are read-heavy systems. For 10 million daily users, feed reads exceed posts by 50:1 ratio.

  • 10 million daily active users open feeds five times daily. This equals 50 million daily feed reads or 600 per second.
  • Users post three times monthly. This results in 1 million daily posts or 12 per second.
  • Focus on optimizing feed reading paths due to high read-to-write ratio.

API Calls for Newsfeed

Mobile apps make API calls on behalf of users. For a newsfeed app, two key endpoints handle posts: create post and get feed. The create post endpoint saves user content, while get feed retrieves posts from followed accounts.

  • When a user creates a post, their phone sends content to the create post endpoint.
  • Opening the app triggers a get feed endpoint call to receive the top 50 posts from followed accounts.
  • The server returns posts from followed accounts only, not all posts in the system.

Database Tables for Posts

Three tables store newsfeed data: users, follows, and posts. The users table includes user IDs, names, and a celebrity flag. The follows table tracks follower relationships. The posts table stores content, author, and timestamp.

  • The follows table has two columns: follower and followed user. With 10 million users, it can reach 2 billion rows.
  • The posts table organizes data by author and time for quick access to recent posts.
  • The celebrity flag in the users table becomes important later for specific feed handling.

Initial Feed Building Problem

The initial approach rebuilds feeds on every app open. This causes excessive database queries: 600 feed opens per second require 180,000 database lookups each second.

  • Peak traffic (5x normal) increases database load to 900,000 lookups per second.
  • Most work is wasted because feeds often don't change between app opens.
  • Rebuilding feeds from scratch for every open creates unnecessary database pressure.

Precomputed Feed Solution

Precompute feeds before users open apps. Store feeds in Redis cache for fast access. When a new post appears, update only the relevant user's feed list.

  • Each user has a feed list in Redis holding post IDs, not full content.
  • When a user posts, a background job adds the post to followers' feed lists in Redis.
  • This avoids rebuilding entire feeds for every app open.

Two-Cache System for Performance

Use two caches: one for feed lists (post IDs) and another for post content. The feed cache holds which posts to show. The post cache stores actual content for quick retrieval.

  • When a user opens the app, the system fetches post IDs from the feed cache.
  • The post cache serves content for these IDs. Missing content is fetched from the database and cached.
  • This system meets the 1-second feed load requirement.

Outbox Pattern for Post Delivery

We use an outbox pattern to safely deliver posts. We save the post content and a delivery note in one database transaction. This ensures both actions succeed or fail together.

  • Save post content to posts table and a delivery note to outbox table within a single transaction.
  • The outbox note includes the post ID and a pending flag.
  • A background worker checks the outbox table every few seconds for pending notes.

Queue Processing and Delivery

The background worker moves pending notes to a queue. Once queued, it marks the note as done. The queue ticket specifies the post and author.

  • Worker drops a ticket into the queue for each pending outbox note.
  • After queueing, the outbox note flag changes from pending to done.
  • Worker checks the follows table to find all followers of the post author.

Handling Duplicate Posts

Duplicate posts can occur if a worker crashes before acknowledging a queue ticket. We handle this by checking for existing post IDs before adding new ones.

  • Worker skips adding a post if its ID already exists in a follower's list.
  • Occasional duplicates after refresh are acceptable per interview guidelines.
  • This avoids wasted work on duplicate entries.

Hybrid Feed Approach

We use a hybrid approach to balance performance. Normal users (under 100,000 followers) get precomputed feeds. Celebrities (over 100,000 followers) use 'fan out on read'.

  • Normal accounts: Posts pushed to follower lists immediately.
  • Celebrity accounts: Posts fetched directly when user opens the app.
  • System merges precomputed posts with direct celebrity fetches for the feed.

Cache Requirements

We need two caches: one for follower lists and one for posts. Cache sizes depend on active users and post volume. Active users are defined as those who opened the app in the last 30 days (configurable).

  • First cache: 40 GB for active users with 500 posts per list (4 KB per user).
  • Second cache: ~30 GB for 30 million monthly posts (1 KB per post).
  • Caches store only active users' data (last 30 days).

Database and Sharding

We use different databases for different data types. Posts use Cassandra for time-ordered data. User and follow data use relational databases.

  • Posts are never updated or deleted, growing to 360 million yearly.
  • Sharding splits posts across multiple database machines.
  • Cassandra handles posts well due to their read-heavy, time-ordered nature.

Media Storage

Images and videos are stored separately from text posts. We don't store media in the main database.

  • Media uses dedicated storage systems (not specified in transcript).
  • This avoids bloating the main database with large media files.

Storing Media Efficiently

Store image and video links in the database, not the media itself. This prevents database bloat and keeps the system lightweight.

  • Database rows contain post text and media URLs only. The app loads media from object storage like S3.
  • CDNs cache media for faster delivery. Users download images directly from the CDN, not the database.
  • Post cache stores media URLs to avoid performance impact from heavy media files.

Handling Viral Posts

Viral posts strain single cache instances. Distribute reads across multiple cache copies to handle extreme traffic.

  • A single cache cannot handle global reads for viral posts. Copy the post to multiple cache instances.
  • This distributes load and prevents cache overload during viral events.
  • Viral posts are served from multiple cache copies to maintain performance.

Celebrity Feed Optimization

Celebrities' posts are pulled from shared cache lists, not the database, to reduce load for all users.

  • Store recent celebrity post IDs in a single shared cache list per celebrity. For example, one list for Leonel Messi.
  • All followers of a celebrity access the same list, avoiding 800 separate database queries.
  • This handles millions of followers without database overload during celebrity posts.

Feed Latency Improvements

Reduce feed latency by prioritizing active users during post distribution.

  • Measure time between database save and follower list update to identify bottlenecks.
  • Add worker nodes to process queue in parallel for faster post distribution.
  • Prioritize active users: push posts to active followers first, then others in a second pass.

Implementing Ranked Feeds

Ranking requires real-time scoring at read time, not precomputation.

  • Score candidates using current metrics: post age, likes, comments, and user interaction history.
  • Score only top 500 candidates to keep processing fast and efficient.
  • Ranks change frequently as likes and comments update, causing post positions to shift.
