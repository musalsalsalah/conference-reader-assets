The Talk's Title and Approach

Kevlin Henney's talk title is straightforward: 'The Past, Present and Future of Programming Languages.' He admits it's prosaic, avoiding witty alternatives. The talk covers historical context, current trends, and future projections without claiming to predict the future.

  • The title was chosen for simplicity, not cleverness. Henney acknowledges it's 'what it says on the tin.'
  • Predictions are framed as projections, not forecasts. Henney humorously notes that many past predictions were never recorded to avoid embarrassment.
  • The talk aims to find a throughline through programming history, highlighting overlooked trends and patterns.

John Backus and Functional Programming

John Backus, Turing Award winner in 1977, discussed functional programming in his speech. He criticized Fortran's origins as a lab experiment that 'zombied' into widespread use.

  • Backus introduced an algebra for functional programming, calling it a 'compositional style.' His speech was the longest Turing Award talk ever.
  • The term 'paradigm' for programming styles was coined by Robert Floyd in 1978, not used in 1977.
  • Backus's 1977 concerns about programming languages' 'trouble' feel eerily current, as if written for 2025.

The Incumbent Effect in Language Adoption

Popular languages grow through compounding usage. More code written in a language means more maintenance and new development in that language. This creates a self-reinforcing cycle.

  • Dijkstra's observation holds: only two language types exist. Languages people complain about and those nobody uses.
  • Existing codebases drive language adoption. New projects often use the same language as existing systems for compatibility.
  • The more a language is used, the more code it accumulates. This creates a multiplier effect for its continued dominance.

Algol 68's Influence

Algol 68, though rarely used today, influenced many modern concepts. It introduced ideas like 'int' for integer, sum types (unions), and structured programming. Its complexity was considered high at the time but is minimal compared to modern languages.

  • Algol 68 coined 'int' for integer. It distinguished integer types using 'short' and 'long'.
  • It introduced sum types (unions) that differ from C's memory overlays. This concept resembles Rust's approach.
  • Algol 68's language definition is shorter than modern C or JavaScript standards. Complexity tolerance has increased over time.

Structured Programming Origins

Structured programming emerged from Algol 68 and early languages. Dijkstra's 'go to statement considered harmful' (1968) was a provocative title added by editor Niklaus Wirth. The 1972 book by Dahl, Dijkstra, and Hoare introduced data structures and early object-oriented concepts.

  • Dijkstra's 1968 paper was titled 'go to statement considered harmful' due to editor Niklaus Wirth's addition of the provocative title.
  • The 1972 book included early object-oriented concepts under the term 'structure'.
  • Programmers at the time used Fortran, which lacked data structures and abstraction features.

Early Programming Notation

Plankalkül (1948) by Konrad Zuse introduced structured programming concepts before the era of teletypes. It featured a sorting function using bubble sort and early control structures like 'Wiederholen' (while loop) with guard conditions.

  • Plankalkül used 'Wiederholen' for while loops. It lacked 'else' statements, requiring negated conditions.
  • The language included a French word 'fun' for 'end' and 'break' in German contexts.
  • Plankalkül's sorting algorithm was a bubble sort variant, typical for 1940s computing.

Algol 60 and the Invention of 'else'

Algol 60 introduced 'else' as a programming construct, but its history involves German translations and early workarounds. Fortran 77 lacked standard 'else' support, requiring extensions for similar functionality.

  • Fortran 77 had no standard 'else'—programmers used nested 'if' statements as workarounds. Any 'else' in Fortran 77 was an extension, not the standard language.
  • The first 'else' appeared in German-translated Algol 58 documents as a descriptive alternative, not as a programming construct. It was not a German translation of 'else' but a technical description.
  • Algol 60's 'if either' structure allowed cascading conditions, unlike modern 'if-else' syntax. This evolved into the familiar 'if-else' pattern we use today.

Co-routines and Their History

Co-routines, invented by Melvin Conway in 1958, were foundational for concurrent programming. They were overshadowed by subroutines but are now resurfacing in modern languages.

  • Conway's 1958 paper introduced co-routines for compiler design. Knuth later described them as symmetric alternatives to subroutines in 1960s.
  • Clu (1973) implemented iterators as constrained co-routines. Python and C# later adopted similar syntax for generators, though C# called them 'state machines'.
  • C++ 20 added co-routine support but with no standard library integration. C++ 23 still lacks meaningful library support, requiring developers to wait until the 2030s.

Simula and Object-Oriented Programming

Simula 67 introduced classes with concurrency as a core pillar. Early object-oriented design included encapsulation, inheritance, polymorphism, and concurrency.

  • Simula 1 (1965) used processes as co-routines for simulation. Each process had data attributes and an operating rule, forming a life cycle.
  • Concurrent programming declined in the 1980s, removing impetus for task libraries. Simula's task library was never standardized due to this decline.
  • Algol 60's block structure inspired classes. Local data in blocks could be returned with behavior, forming the basis of object-oriented design.

Encapsulation and Data Abstraction

Simula introduced data and functions together in a capsule, defining early encapsulation. This differed from modern object-oriented concepts, as Simula lacked data hiding until Simula 86 added the 'hidden' keyword.

  • Simula 86 introduced data hiding with the 'hidden' keyword, a feature C++ later adopted for data protection.
  • Data abstraction, formalized by Barbara Liskov in 1974, defines objects by their behavior, not implementation details.
  • Liskov's Turing Award recognition highlighted how her work on abstract data types became foundational, despite being overlooked initially.

CSP and Channels

CSP (Communicating Sequential Processes), introduced by Tony Hoare in the late 1970s, defined processes as units of encapsulation with state and behavior. Channels, not methods, enabled process communication.

  • Occam 2, an implementation of CSP, featured a strict type system that made Rust's type safety seem weak by comparison.
  • Occam enforced immutability, making Haskell's approach look lenient, and required programs to compile correctly to function properly.
  • Multiple assignment (a, b = c, d) originated in 1963 with CPL, later appearing in Clue, Occam, and Python.

Functional Programming Trends

Functional programming languages remain a small subset of popular languages, with Haskell being the only purely functional language. Declarative programming, including SQL and LINQ, is more widespread.

  • Simon Peyton Jones noted Excel's widespread use of functional programming, as accounts departments perform functional programming daily through spreadsheets.
  • Lambda calculus, formalized by Alonzo Church in 1936, underpins functional programming concepts, with Excel adopting lambdas in 2020.
  • Excel's adoption of lambdas in December 2020 followed Microsoft's announcement, spreading to Google Sheets.

Lisp's Early Influence

Lisp pioneered lambda expressions in the early 1960s, appearing in Lisp 1.5 Programmer's Manual. This predates most modern languages. The original Lisp used a chained condition structure, unlike later versions with if-else forms.

  • Lisp 1.5 (1960s) introduced lambda expressions before other languages adopted them.
  • Original Lisp lacked if-else syntax, using multi-way conditions instead. Later versions added standard conditional forms.
  • Lisp's AI association shaped early programming language development, especially in machine learning contexts.

Language Evolution Trends

Programming languages borrow features from each other rather than innovate from scratch. Each new language incorporates predecessors' features with minor improvements. This cross-fertilization is common in modern language design.

  • Java adopted lambdas later than C# and JavaScript, which had them in the 1990s.
  • Lisp (1960s) was the first to use lambda expressions, with Smalltalk 80 being an early object-oriented language.
  • Modern languages blend existing ideas rather than introduce entirely new paradigms.

AI's Impact on Language Adoption

LLMs train on existing code, amplifying bias toward established languages. This creates a feedback loop where new languages struggle to gain traction. The industry's focus on change contradicts LLMs' inherent inconsistency.

  • LLMs use existing languages like Python and Pandas for code generation, not new ones.
  • LLMs cannot replace compilers due to lack of consistency in output. Code requires deterministic behavior.
  • The industry guarantees inconsistent code generation, making LLMs unsuitable for direct code replacement.

The Future of Programming

Despite claims of AI liberation from mainstream languages, evidence shows the opposite. LLMs reinforce existing language dominance. The industry's focus on change contradicts the need for code consistency.

  • AI does not eliminate the need for established languages. LLMs rely on existing codebases for training.
  • Code requires determinism for business-critical systems. LLMs cannot guarantee consistent output.
  • The von Neumann architecture remains dominant, with no significant shift toward declarative programming.

The Past's Influence

The past influences programming language evolution significantly. It acts as a silent partner with a very big vote in design decisions.

  • Many theoretical possibilities never become reality due to historical constraints.
  • The past's influence is silent but powerful, affecting choices without direct acknowledgment.
  • Only a few language features actually transpire despite many possible options.

Reality vs. Possibility

Many programming language ideas are theoretically possible, but only a few become reality. The gap between potential and actual implementation is significant.

  • Theoretical possibilities often fail to materialize due to practical constraints.
  • Designers must balance innovation with feasibility to create viable languages.
  • Most language features remain conceptual rather than implemented in practice.
