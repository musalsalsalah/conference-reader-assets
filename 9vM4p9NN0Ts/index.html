Stanford CS229 I Machine Learning I Building Large Language Models (LLMs)

What Are LLMs?

Large language models (LLMs) power modern chatbots like ChatGPT, Claude, Gemini, and Llama. They're neural networks trained to model language probability distributions. The lecture focuses on practical training components beyond architecture.

  • LLMs are neural networks that predict next tokens in sequences. They model language as probability distributions over tokens.
  • Examples include ChatGPT (OpenAI), Claude (Anthropic), Gemini, and Llama. These are all LLM-based chatbots.
  • The lecture emphasizes data, evaluation, and systems over architecture. Industry prioritizes these practical aspects.

Key Training Components

Five key components define LLM training: architecture, training loss/algorithm, data, evaluation, and systems. Architecture is less critical than other factors in practice.

  • Architecture: Neural network structure (e.g., transformers). Lecture skips this due to prior coverage and abundant online resources.
  • Training loss: Cross-entropy loss maximizes text likelihood during training.
  • Data: Models train on vast text corpora, like internet content.
  • Evaluation: Measures progress toward LLM goals, not just accuracy.
  • Systems: Hardware efficiency for large models, increasingly critical in practice.

Pretraining vs. Posttraining

Pretraining models internet-scale language patterns. Posttraining adapts models into AI assistants (e.g., ChatGPT). Pretraining uses language modeling; posttraining uses alignment techniques.

  • Pretraining: Classic approach (GPT-2, GPT-3). Models predict next tokens across vast text data.
  • Posttraining: Recent trend (ChatGPT). Adapts pretrained models into conversational assistants.
  • Pretraining focuses on language modeling tasks. Posttraining focuses on user interaction alignment.

Autoregressive Language Models

Autoregressive models predict next tokens sequentially. They decompose language probability using chain rule. This approach has generation speed trade-offs.

  • Task: Predict next token given previous context. Example: 'she likely prefers' → 'dogs'.
  • Tokenization converts text to IDs. Vocabulary size equals model output dimensionality.
  • Training uses cross-entropy loss. Maximizes log likelihood of training text.
  • Inference samples from probability distribution. Training predicts most likely token.

Tokenization Importance

Tokenizers convert text to manageable units. They handle typos, non-space languages, and vocabulary size. Tokenization is critical but often overlooked.

  • Problem: Word-based tokenization fails with typos or languages like Thai without spaces.
  • Solution: Use subword or character-level tokenization. Handles unknown words and new vocabulary.
  • Vocabulary size determines model output dimension. Large vocabularies require careful management.

Tokenization Basics

Tokenizers split text into smaller units to manage sequence length. Long sequences cause quadratic complexity in transformers. Tokenizers assign unique IDs to common subwords, keeping character-level tokens for typos or errors.

  • Tokenizers merge common character pairs like 't' and 'o' into new tokens. This reduces sequence length while preserving meaning.
  • Each token has a unique ID. For example, 'bank' (money) and 'bank' (water) share a token but the model distinguishes meaning from context.
  • Pre-tokenizers handle spaces and punctuation separately for efficiency. This avoids unnecessary merging across word boundaries.

Byte Pair Encoding

Byte Pair Encoding (BPE) is a common tokenization method. It starts with character-level tokens and merges frequent pairs iteratively. This creates a compact vocabulary for large text corpora.

  • BPE trains on massive text data. The tokenizer splits 'tokenizer' into two tokens: 'token' and '-izer'.
  • The process merges the most frequent token pairs. In a small example, 'to' appears three times and becomes a new token.
  • BPE keeps smaller tokens like 't' and 'o' even after merging. This ensures representation of typos or uncommon words.

Tokenization Challenges

Tokenization affects model performance, especially with numbers and code. Current methods struggle with mathematical expressions and programming syntax.

  • Numbers like '327' often get a single token. This prevents models from understanding numerical patterns like addition.
  • GPT-4 improved code tokenization. It handles Python's four-space indentation better than previous models.
  • Future models might move away from tokenizers if architectures scale better with sequence length.

Model Evaluation

Perplexity measures model uncertainty. It's the exponentiated average loss per token. Lower perplexity means better prediction accuracy.

  • Perplexity ranges from 1 (perfect prediction) to vocabulary size (random guessing). Modern models have dropped from ~70 to under 10 perplexity since 2017.
  • Academic benchmarks like MMLU test model knowledge across domains. Questions cover topics like college physics and astronomy.
  • MMLU evaluates by comparing likelihood of correct answers. Models must choose between multiple options for each question.

Evaluation Benchmarks

HELM and Hugging Face's leaderboard are common academic benchmarks. They aggregate results across multiple NLP tasks for comprehensive evaluation.

  • HELM includes question-answering tasks with known correct answers. Models are scored on how likely they are to generate the right response.
  • MMLU is the most common benchmark. It tests knowledge in fields like medicine, physics, and astronomy with multiple-choice questions.
  • Perplexity is still used for model development but not for academic comparisons due to tokenizer dependency.

Evaluating Model Predictions

To evaluate model responses, constrain output to specific options like A, B, C, D. This involves prompting the model and comparing only those tokens' probabilities without sampling.

  • Prompt the model with choices A, B, C, D to limit response options.
  • Compare the model's probability distribution for these tokens directly.
  • This method avoids generating full responses and focuses on the most likely token.

Perplexity and Tokenization

Perplexity depends on tokenization choices. A larger vocabulary size increases the upper bound of perplexity, making direct comparisons between models with different tokenizers misleading.

  • ChatGPT with 10,000 tokens has a lower perplexity upper bound than Gemini with 100,000 tokens.
  • Tokenization design choices affect perplexity metrics, so they are not reliable for cross-model comparison.
  • Perplexity ranges between 1 and the vocabulary size, making it sensitive to tokenizer differences.

Benchmarking Inconsistencies

Benchmarking methods vary widely, causing inconsistent results. For example, Llama-65b showed 63.7% accuracy on HELM but 48.8% on another evaluation method.

  • Different organizations use different evaluation methods for the same benchmark like MMLU.
  • This leads to significant accuracy differences for the same model across evaluation methods.
  • Prompting techniques also affect evaluation results, adding complexity.

Train-Test Contamination

Train-test contamination occurs when test data appears in training data, skewing results. This is critical for academic research but less so for company development.

  • Check if test set examples are more likely to generate in original order than shuffled order.
  • Use web crawlers like Common Crawl to collect data, which includes 250 billion pages and 1 petabyte of data.
  • Common Crawl data is often messy, with incomplete sentences and HTML formatting.

Data Processing Pipeline

Raw internet data requires extensive processing before training. This includes text extraction, filtering, and de-duplication to create high-quality training data.

  • Extract text from HTML, removing headers, footers, and boilerplate content.
  • Filter out undesirable content like harmful material and PII using blacklists or small classifiers.
  • De-duplicate content to remove repeated sections from forums or books.
  • Apply heuristic filtering to remove low-quality documents based on token distribution or length.

Domain Weighting and Quality Focus

After processing, data is classified into domains like books, code, or entertainment. Models are then weighted to emphasize high-quality or useful domains.

  • Use Wikipedia links to identify high-quality websites for domain classification.
  • Code and book domains are often upweighted to improve reasoning and language skills.
  • Entertainment domains are typically downweighted to reduce irrelevant content.
  • Final training often overfits on high-quality data like Wikipedia to refine model performance.

Data Collection Challenges

Data collection is the most critical part of training large language models. Companies keep their data processing methods secret due to copyright risks and competitive advantages. Filtering internet data reduces it significantly before training.

  • Initial data starts at 150 billion tokens (800GB), filtering to 15 trillion tokens for top models like Llama 3.
  • Llama 2 used 2 trillion tokens while Llama 3 uses 15 trillion tokens, matching the largest academic benchmarks.
  • Common Crawl requires 100-1,000x filtering to reach usable data volumes.

Data Processing Scale

Data processing requires massive compute resources. A typical team might have 15 people dedicated to data work out of a 70-person team.

  • Data processing needs more CPUs than model training requires, making it compute-intensive.
  • Companies avoid discussing data methods due to copyright liability risks from using books or other protected content.
  • Synthetic data generation and multimodal data are emerging approaches to address data scarcity.

Scaling Laws

Scaling laws show that larger models and more data consistently improve performance without overfitting. This contradicts traditional machine learning teaching about overfitting.

  • Test loss decreases predictably when increasing compute, data size, or model parameters on log scale.
  • Scaling laws allow predicting performance for future models based on compute investment.
  • No empirical evidence of performance plateauing yet, though theoretical limits may exist.

Practical Scaling Strategies

Modern training pipelines use scaling laws to optimize resource allocation. Companies now predict model performance before full-scale training.

  • Instead of training full models for short periods, teams test smaller models at different scales first.
  • Scaling laws help compare architectures like transformers versus LSTMs before committing to full training.
  • The slope and intercept of scaling curves determine which architecture performs better at scale.

Scaling Laws and Model Training

Scaling laws show that architecture choices like activation functions have minimal impact compared to data quality and compute resources. Minor architectural changes only affect the intercept of scaling curves, not overall performance. Training longer or using better hardware often outweighs architectural tweaks.

  • Data quality directly affects scaling law performance. Good data produces significantly better results than bad data, making it more important than architecture adjustments.
  • Chinchilla found 20 tokens per parameter is optimal for training efficiency. This means adding one parameter requires 20 more training tokens to maintain optimal scaling.
  • Inference costs influence real-world decisions. Production models use 150 tokens per parameter to balance training and inference costs, reducing long-term expenses.

Resource Allocation and Cost Analysis

Optimal resource allocation depends on compute constraints. Scaling laws help determine whether to increase model size or data volume for best results. Real-world costs include training, inference, and environmental impact.

  • Llama3 400B used 15.6 trillion tokens and 405 billion parameters. Its training required approximately 3.8e25 flops, just below the 1e26 threshold for regulatory scrutiny.
  • Training cost estimates: $52 million for GPU rental (26 million hours at $2/hour) plus $25 million in salaries for 50 employees, totaling ~$75 million.
  • Environmental impact: ~4,000 tons of CO2 equivalent, equivalent to 2,000 round-trip flights from JFK to London. This is significant but not yet a major concern for current models.

Alignment and Post-Training

Post-training transforms language models into helpful assistants. Pure language models often fail to provide direct answers, instead continuing internet-style content patterns. Alignment ensures models follow user instructions and avoid toxic outputs.

  • Without alignment, a pure language model like GPT-3 would respond to 'explain the moon landing to a six-year-old' with 'explain the theory of gravity to a six-year-old'—continuing patterns rather than answering directly.
  • Alignment goals include making models follow user instructions and avoid harmful content. This transforms models from language predictors into helpful AI assistants.
  • OpenAI's approach with ChatGPT demonstrates successful alignment, making models responsive to user needs rather than continuing text patterns.

Supervised Fine Tuning (SFT)

SFT aligns models by fine-tuning pretrained LLMs on human-collected question-answer pairs. This approach uses minimal data since the model already knows language structure from internet-scale pretraining.

  • Human data is expensive to collect but essential for desired outputs. Example: A human provided a correct answer about monopsony for a question about market structures.
  • Pretraining provides language knowledge. SFT specializes the model for specific user types without adding new facts.
  • SFT uses the same language modeling loss as pretraining. It's called 'supervised' because it uses human-labeled answers.

Synthetic Data Generation

Synthetic data speeds up development by using LLMs to generate question-answer pairs from human examples. This reduces human effort but requires careful handling.

  • Alpaca used 175 human questions to generate 52,000 synthetic pairs via text-davinci-003. Fine-tuned on Llama 7B, it replicated ChatGPT's success.
  • LLM-generated data remains effective even after multiple generations. Example: Algorithm definitions from synthetic data matched human quality.
  • Over-reliance on synthetic data risks bootstrapping the same distribution. Human edits on LLM outputs improve quality without full human input.

Data Efficiency Limits

SFT requires surprisingly little data. Scaling from 2,000 to 32,000 examples shows diminishing returns, as models already know most content from pretraining.

  • LIMA study shows 2,000 high-quality examples suffice. More data doesn't significantly improve performance.
  • SFT teaches formatting, not new knowledge. The model specializes for specific user types seen during pretraining.
  • Human-in-the-loop editing (e.g., fixing LLM outputs) adds value faster than full human data collection.

RLHF for Better Alignment

RLHF addresses SFT limitations by maximizing human preferences instead of cloning human answers. This avoids hallucinations and improves output quality.

  • SFT can cause hallucinations when models mimic plausible but incorrect references. Example: A human writes a reference that the model didn't see during pretraining.
  • RLHF uses model-generated answers for comparison. Humans rank which response better matches their preferences.
  • RLHF avoids human data bottlenecks. Humans only evaluate model outputs, not create full answers.

Reinforcement Learning for LLM Fine-Tuning

LLMs improve responses using reinforcement learning based on human preferences. Two main approaches exist: binary rewards and reward models. Both methods refine outputs using human feedback.

  • Binary rewards compare model outputs against a baseline. Humans label which response is better with +1 or -1. This sparse feedback provides limited detail about response quality.
  • Reward models classify preference strength between two outputs. They output continuous values instead of binary labels, offering more nuanced feedback for training.
  • Reward models use a Bradley-Terry model approach. They generate logits representing preference strength, allowing models to learn how much better one response is than another.

PPO Implementation Challenges

PPO (Proximal Policy Optimization) was used in early ChatGPT development. It involves supervised fine-tuning, reward model training, and iterative PPO updates.

  • PPO requires collecting human preferences, training a reward model with maximum likelihood, and applying reinforcement learning. This creates a complex pipeline with many implementation challenges.
  • PPO implementation involves technical complexities like rollouts, outer loops, and clipping. These make it difficult to implement correctly in practice.
  • PPO changes LLM training. Instead of maximizing likelihood, models optimize for preferred responses, losing meaningful likelihood scores for text.

DPO: Simplified Alternative to PPO

DPO (Direct Preference Optimization) simplifies training by directly maximizing preferred responses without reinforcement learning. It's mathematically equivalent to PPO under certain assumptions.

  • DPO uses maximum likelihood to maximize probability of preferred responses and minimize probability of less preferred ones. This eliminates reward models and reinforcement learning steps.
  • DPO is simpler to implement than PPO. It requires only one training step instead of multiple complex steps involving reward models and reinforcement learning.
  • DPO performs as well as PPO in practice. It's now the standard approach in both open-source and industry settings for preference-based LLM training.

Data Collection for Preference Training

Collecting human preference data is complex and requires detailed guidelines. Labelers must evaluate subtle differences between model responses.

  • Labeling examples require careful comparison of similar responses. For instance, two descriptions of self-driving cars might both seem correct but have subtle differences in detail.
  • Human labeling is time-consuming and difficult. The process requires significant effort to ensure consistent preference data.
  • Preference data collection is essential for both PPO and DPO training. It provides the human feedback that guides model improvement.

Human Data Challenges

Human data collection for LLM training faces multiple issues. Humans often prioritize superficial features like output length over correctness, leading to biased preferences in RLHF that cause models to generate longer responses.

  • Humans agree with themselves only around 66% of the time on binary labeling tasks. Experts discussing labeling for three hours achieved 67-68% accuracy.
  • Crowdsourcing ethics are problematic. Annotators often receive low pay and handle toxic content while labeling.
  • Human labeling costs approximately $300 per 1,000 examples on platforms like Mechanical Turk.

LLM-Generated Preferences

Replacing human preferences with LLM-generated ones improves efficiency and consistency. Models show higher agreement with human preferences than humans do themselves due to less variance.

  • Models cost about 50x less than humans for labeling and achieve better agreement with human preferences than humans do.
  • Models have less variance than humans but may introduce bias. This approach is now standard in open-source communities.
  • Industry uses hybrid approaches combining both human and LLM preferences for RLHF data collection.

Model Evaluation Methods

Traditional metrics like validation loss and perplexity don't work for aligned LLMs. Evaluation requires human-like preference comparisons between model outputs.

  • ChatBotArena uses real users to compare model outputs. It's the most trusted benchmark but expensive at scale.
  • AlpacaEval uses LLMs to evaluate models. It correlates 98% with human evaluations and costs under $10 for 3 minutes of processing.
  • LLMs prefer longer outputs, which humans also favor. This bias can be controlled through causal inference techniques.

Evaluation Biases

LLM evaluations suffer from spurious correlations. Output length significantly impacts win rates, requiring bias correction.

  • When prompted to be verbose, models achieve a 64.4% win rate versus 20% when concise.
  • Without correction, verbose outputs gain unfair advantage in evaluations.
  • Causal inference tools control for length, reducing its impact on evaluation results.

Training Data Scale

RLHF requires significantly more data than SFT. This data volume influences model weights despite being small compared to pretraining.

  • SFT typically uses 5,000-50,000 examples. RLHF uses around 1 million examples.
  • Pretraining involves 15 trillion tokens, making RLHF data volume relatively small.
  • Industry fine-tunes all weights, while open-source may use techniques like LoRA to modify specific weights.

Model Initialization and Fine-Tuning

Pretraining serves as model initialization, not a separate data phase. After pretraining, fine-tuning uses only post-training data. The model's weights are the key, not prior training data.

  • Pretraining initializes weights. Fine-tuning starts from this point.
  • Overfitting a single sentence is possible with large learning rates and sufficient training time.
  • The number of fine-tuning epochs isn't critical. Effective learning rate matters most.

GPU Architecture and Optimization

GPUs optimize for throughput, not latency. They excel at parallel matrix operations but face memory and communication bottlenecks.

  • GPUs use streaming multiprocessors for high-throughput parallelization.
  • Matrix multiplication runs 10x faster on GPUs than other operations.
  • Compute improves faster than memory, causing GPU idle time without optimization.

Model FLOP Utilization

Model FLOP utilization measures GPU efficiency. 50% utilization is excellent; industry examples like Llama achieve 45%.

  • Low precision reduces data transfer size and speeds up communication.
  • 16-bit precision is standard for computation. Weights remain in 32-bit storage.
  • Automatic mixed precision uses 32-bit weights but 16-bit computation for speed.

Operator Fusion

Operator fusion reduces communication overhead by combining operations. PyTorch's torch.compile can double speed by fusing kernels.

  • Naive code moves data between memory and GPU for each operation.
  • Fused kernels communicate once, perform all operations, then return data.
  • torch.compile rewrites PyTorch code to C++/CUDA for efficiency.
