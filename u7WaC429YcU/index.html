Evolution of software architecture with the co-creator of UML (Grady Booch)

Rise of Abstraction Levels

Software engineering history shows rising abstraction levels. Modern frameworks embody past architectural decisions. Architects now choose cloud services, messaging systems, and platforms with economic implications.

  • Architects face systemic problems, not just software issues. Decisions now involve economic factors like cloud service costs.
  • Legacy code persists indefinitely. Even Facebook and Google maintain legacy systems with technical debt.
  • IRS systems still contain IBM 360 Assembly code. This code embodies business rules, making updates difficult.

Grady Booch's Background

Grady Booch co-created UML and originated object-oriented analysis and design. He's an IBM Fellow with decades of software engineering work. His career spans from building computers at age 12 to modern AI research.

  • Booch built his first computer at 12. He's authored six books and over 100 technical papers.
  • IBM Fellow status provides freedom to pursue long-term research. Only 89 active fellows remain among 350 total.
  • He moved from Rational Software to IBM Research in 2003. His focus shifted to AI around 2010.

Legacy Systems Challenge

Legacy systems exist from the moment code is written. They require ongoing maintenance. Modern organizations face similar challenges as historical systems like IRS and banks.

  • IRS systems contain code written in the 1960s. Some still uses IBM 360 Assembly Language.
  • Legacy code embodies business rules. Changing it requires solving human problems, not just technical ones.
  • Financial institutions maintain codebases from the 1960s. This creates ongoing technical debt.

Defense Systems Origins

Modern computing emerged from defense systems like SAGE. This Cold War-era project triggered the first golden age of software engineering.

  • SAGE system (1950s-1980s) responded to Soviet bomber threats. It required real-time processing.
  • SAGE led to NATO conferences on software engineering. This marked the start of the first golden age.
  • Defense systems preceded commercial computing. Modern systems evolved from military projects.

Architectural Evolution

Software architecture evolved from algorithmic languages to modern frameworks. The first golden age focused on structured analysis for monolithic systems.

  • First golden age used Fortran, COBOL, APL, and Lisp. Systems were non-distributed monoliths.
  • Structured analysis techniques emerged from figures like Yourdon and DeMarco.
  • Modern frameworks handle architectural decisions that were once front-and-center for architects.

Distributed Systems Emergence

The first golden age of software engineering shifted as distributed systems emerged, primarily in defense and government sectors. The Arpanet, funded by DARPA, enabled early email networks. Grady Booch taught at the Air Force Academy in 1979 with a mimeographed list of global email addresses.

  • Arpanet, funded by DARPA, enabled early email networks with only a few thousand addresses globally in 1979.
  • Booch taught at the Air Force Academy in 1979 using a mimeographed list of email addresses for communication.
  • Defense systems like the Telemetry Integrated Processing System used 32 mini-computers, creating early distributed system challenges.

Ada Programming Language

The U.S. Department of Defense faced software complexity due to thousands of programming languages. Ada was created to unify development, influenced by Simula and Smalltalk.

  • Ada was designed to replace thousands of programming languages used by the federal government in the late 1970s.
  • Ada incorporated ideas from Simula and Smalltalk, which viewed the world through different lenses.
  • Ada included information hiding concepts from David Parnas, now standard in modern software engineering.

Booch Method Origins

The Booch Method emerged from the need to manage distributed systems and Ada programming. It shifted focus from algorithmic decomposition to object-oriented design.

  • The Booch Method redefined software architecture by focusing on classes and objects instead of algorithms.
  • Early object-oriented concepts existed in COBOL's common data areas but lacked language support until Ada.
  • Booch learned about distributed systems while working on the Telemetry Integrated Processing System with 32 mini-computers.

Booch Method Evolution

The Booch Method initially emphasized inheritance but later recognized its overuse. Its core principles, like class-based abstractions, became foundational for modern object-oriented programming.

  • Inheritance was overemphasized in early Booch Method implementations, leading to unnecessary complexity.
  • Class-based abstractions from the Booch Method are now standard in how developers view software architecture.
  • The method's influence persists in the very atmosphere of modern software engineering.

Rational Software Creation

Rational Software was founded in 1982 by Grady Booch, Paul Leary, and Mike DeVin. They aimed to create an Ada development environment for defense projects.

  • Rational Machines Inc. was founded in 1982 to build an Ada development environment for defense projects.
  • Mike DeVin designed the R1000 system, the dominant Ada development tool in the early 1980s.
  • Venture capitalists Art Rock and H. Quist, founders of Apple, supported Rational's early funding.

Booch and C++ Collaboration

Grady Booch met Bjarne Stroustrup after a lecture, discovering shared work on object-oriented design. Stroustrup's C with Classes evolved into C++, and early editions referenced Booch's ideas.

  • Stroustrup's first C++ book referenced Booch's methods, not the other way around.
  • Booch's book on object-oriented design later cited Stroustrup's work, showing mutual influence.
  • Their collaboration began with a question from Stroustrup at a lecture, leading to joint lectures and shared references.

Rational's Commercial Shift

Rational Software shifted from defense to commercial sectors after Booch advised against focusing on embedded systems. This led to Rational Rose, a design tool for Booch diagrams.

  • Booch rejected Rational's embedded systems plan, urging focus on commercial markets instead.
  • Rational Rose was prototyped in Smalltalk and ran on IBM PCs before Windows support.
  • The tool allowed teams to draw Booch diagrams to reason about designs, not UML.

UML's Development

UML emerged from unifying Booch, Rumbaugh, and Jacobson's methodologies. It was released to the Object Management Group as UML 1.0, emphasizing visual reasoning.

  • Booch, Rumbaugh, and Jacobson combined their methods into UML 1.0, with Booch driving the primary document.
  • UML 1.0 was defined as a visual language for reasoning about systems, not a programming tool.
  • Booch actively pushed back against UML being seen as a programming language, stressing its role in visual reasoning.

Rational Unified Process

Philippe Kruchten contributed the four-plus-one view model to Rational Unified Process, emphasizing multiple perspectives on architecture.

  • Kruchten's model included use cases, logical, process, implementation, and deployment views.
  • This model later influenced the ISO/IEC 4220 standard for architectural description.
  • Kruchten's work stemmed from building Canada's Air Traffic Control System, a complex distributed system.

UML's Misunderstandings

UML was often misinterpreted as a programming language, contrary to Booch's intent. He advocated for using UML diagrams to reason about systems, not as code.

  • Booch insisted UML diagrams should be discarded after use, not treated as permanent code.
  • UML 2.0 introduced precision demands from a faction, leading to over-engineering.
  • Many users failed to discard UML diagrams, treating them as code instead of thinking tools.

UML's Evolution and Decline

Grady Booch, co-creator of UML, reflects on its development and decline. UML was never intended as a programming language, but its misuse for code generation and reverse engineering made it overly complex. This shift marked the beginning of UML's decline.

  • UML peaked at 20-30% market penetration around 2000, used by major companies like IBM and Microsoft.
  • Microsoft integrated UML into Visual Studio around 2000, helping customers build complex distributed systems.
  • IBM acquired Rational (UML's creator) for $2.7 billion in 2003, absorbing a 3,500-person team with $1 billion in revenue.

Microsoft's Internal Struggles

Booch declined Microsoft's offer to become Chief Architect for Enterprise. He cited Microsoft's dysfunctional internal structure, with competing groups like Office and Windows holding 'guns' against each other.

  • Bill Gates offered Booch the role in 2003, but Booch refused due to Microsoft's internal conflicts.
  • Booch noted Microsoft's 'nasty' culture, with teams unable to collaborate, making him unwilling to 'fix it'.
  • A cartoon depicted Microsoft's internal divisions, with teams holding guns at each other.

Modern Software Architecture

Booch explains today's software architecture has shifted. Most systems use pre-built frameworks, reducing the need for deep architectural thinking. UML is now used only in high-risk, high-complexity scenarios.

  • Architecture decisions are often pre-made by frameworks like RabbitMQ or Redis, requiring architects to weave components together.
  • High-risk systems like missile control or financial systems still use UML for formalism due to accountability needs.
  • Startups and scale-ups often reject UML, favoring 'disposable software' with minimal ceremony.

Economics of Software Development

Software architecture's evolution reflects changing economics. Early software required optimization due to expensive machines. Today, cheap computing resources make formal methods less necessary.

  • Booch's personal cloud of four Nvidia boards has more processing power than 1970s global computing capacity.
  • AI and prompt engineering enable 'one-off' systems that don't require architectural planning.
  • Amazon uses formal methods for AWS S3, showing UML's continued relevance in critical systems.

Architectural Patterns in Cloud Services

Amazon and Microsoft codify architectural patterns through visual diagrams and examples. Their documentation shows how to build systems using specific services, reducing the need for rediscovery. This reflects a shift from algorithms to patterns.

  • Amazon uses blocky diagrams to represent system architecture. These diagrams show which services to use for specific system types.
  • Microsoft's Azure documentation provides examples of service combinations. This helps developers avoid reinventing common patterns.
  • Architectural patterns have replaced the need for individual rediscovery of system designs. This represents business maturity in software development.

Formal Methods and Their Limits

Formal methods validate specific system parts but don't cover real-world constraints. They're used in driver validation but don't shape overall architecture.

  • Microsoft uses formal methods for driver validation. This applies to hardware systems where failure risks are high.
  • Formal methods focus on functionality, not space or time constraints. They're limited to specific system components.
  • Architects don't use formal methods for overall system architecture. They're only useful for parts of a system.

Evolution of the Architect Role

The software architect role has evolved from a distinct position to integrated roles like staff engineer. The focus shifted from pure software design to systemic decisions.

  • Mary Shaw's book 'Software Architecture' established architectural patterns as a formal concept. Her work influenced the field's understanding.
  • Architectural decisions now involve economic choices like cloud service selection. This reflects a shift from software-only to systemic considerations.
  • Solutions architects emerged to handle cloud-specific decisions. They make choices about services like AWS EC2 versus other options.

Challenges in System Migrations

Migrations between architectures are hard due to lost design rationale. The code shows what was built but not why decisions were made.

  • Migrations often involve moving from monoliths to microservices or changing technologies like Node to Go. These require significant rethinking.
  • Design decisions are lost when original developers leave or retire. This creates uncertainty during migrations.
  • System drift occurs without a chief decision-maker maintaining conceptual integrity. This is inevitable without active management.

AI's Impact on Software Architecture

AI represents a major shift comparable to distributed systems. It's disrupting how systems are built and managed, similar to the transition from mainframes to distributed computing.

  • The shift to distributed systems required rethinking how systems were built. This was a seismic change that affected all aspects of software development.
  • AI's impact is comparable to the rise of microcomputers and edge devices. These changes compel new architectural approaches.
  • Architectural decisions now must consider edge computing and AI capabilities. This changes where processing occurs in systems.

Early Distributed Systems Era

In the late 1960s and early 1970s, mainframes dominated computing but revealed underutilization. This led to time-sharing systems and real-time computing systems like Whirlwind from Lincoln Laboratories. Miniaturization from defense investments enabled desktop computers, fostering distributed systems in the mid-to-late 1970s.

  • Mainframes were often underutilized, prompting time-sharing systems to maximize resource use.
  • Whirlwind introduced real-time computing, connecting machines to physical systems.
  • Defense-funded semiconductor advances made desktop computers economically feasible.

Client-Server and Distributed Computing Shift

Client-server systems emerged as dumb terminals connected to mainframes, but miniaturization allowed processing to move to edge devices. This shift required new communication methods like RPC or shared memory, creating uncertainty about system design.

  • Dumb terminals (e.g., IBM green screens) initially connected to mainframes, but miniaturization enabled distributed processing.
  • Programmers faced uncertainty: should they use RPC, shared memory, or other communication methods?
  • By the 1980s–1990s, common communication patterns emerged from trial and error.

Watson Jeopardy Architecture

IBM's Watson Jeopardy system, winning in 2011, used a pipeline architecture that brought together statistical systems and knowledge engineering methods—not neural networks. Booch documented this after IBM asked him to analyze its architecture.

  • Watson Jeopardy beat humans in Jeopardy using statistical AI systems, not neural networks.
  • Booch documented Watson's pipeline architecture, which IBM later commercialized.
  • IBM management was warned about Watson's limitations, but overhyped claims led to skepticism.

Mars Mission Robotics Architecture

In 2014, Booch designed a neuro-symbolic architecture called SELF for NASA's Robonaut 2 on the International Space Station. It combined Marvin Minsky's Society of Mind with Rodney Brooks's subsumption architecture and Hofstadter's strange loops.

  • NASA needed robots for Mars missions with no ground control due to light-speed delays.
  • SELF architecture enabled robots to operate autonomously during Mars missions.
  • Booch's team tested SELF with Robonaut 2 for scientific tasks on the ISS.

LLMs and Historical Parallels

Booch compares LLMs to the rise of distributed systems and GPUs. Like TCP/IP and HTML standardized communication, LLMs face similar hype but require careful evaluation of their limits.

  • LLMs are not as transformative as distributed systems but share similar hype cycles.
  • GPUs, initially for gaming, later enabled deep learning through matrix math.
  • Booch warns against overhyping LLMs, citing Watson's limitations as a cautionary example.

Neuro-Symbolic Systems in Robotics

Grady Booch co-created UML and later developed SELF, a neuro-symbolic system combining neural and symbolic components. It powered robotics projects for NASA and Woodside Energy, which faced similar challenges in hazardous environments.

  • SELF integrated neural models for motion tracking with symbolic logic for decision-making. This allowed robots to navigate complex physical spaces safely.
  • Woodside Energy sought to build cooperative robots for oil rigs, a dangerous environment similar to NASA's space robotics challenges.
  • Booch's team grew to 35 people during SELF's peak development. IBM later terminated the project after Watson's financial struggles.

Large Language Models: Capabilities and Limits

Booch acknowledges LLMs' coherence but stresses they're unreliable narrators. They generate text through statistical patterns, not true understanding or reasoning, making them stochastic parrots.

  • LLMs navigate complex latent spaces trained on internet data. This creates coherent outputs without actual comprehension or reasoning ability.
  • Booch and Gary Marcus criticize claims that scaling LLMs will achieve AGI. They argue this underestimates human intelligence's complexity.
  • Elon Musk's self-driving promises highlight LLMs' architectural limitations. Booch compares relying on LLMs for complex tasks to building a nuclear plant for simple tasks.

Embodied Cognition and Future Architecture

Human intelligence evolved through embodiment—interacting with the physical world. LLMs lack this sensory richness, operating primarily through text with minimal multimodal input.

  • The human brain uses cortical columns (7 layers deep in humans) for predictive modeling. LLMs ignore this complexity with simple layering.
  • Emotions and decisions occur in entangled brain architectures involving the thalamus and hormonal systems. LLMs lack these biological mechanisms.
  • Booch studies human brain architecture to inform better AI systems. He believes true AGI requires mimicking biological complexity, not just scaling LLMs.

Architectural Visualization for AI

Booch advocates for standardized architectural visualization tools for LLMs, similar to UML for software. He's exploring AlphaFold 3's architecture as a case study.

  • Current LLM visualizations resemble simple boxes representing message-passing systems. Booch seeks more detailed architectural descriptions.
  • AlphaFold 3's open-source release offers a practical example for developing better AI architecture visualization methods.
  • Booch believes this visualization standard would help engineers understand and improve AI system design beyond current LLM limitations.

Advice for New Software Engineers

Booch advises new engineers not to fear AI tools like GitHub Copilot. Software engineering evolves through higher abstraction levels, not obsolescence.

  • He emphasizes that informed decision-making remains essential regardless of programming language or tools used.
  • Booch sees current AI tools as exciting opportunities, not threats. Computational resources now enable more creative possibilities than ever.
  • He encourages new engineers to focus on imagination and problem-solving, as these skills will always be valuable in software development.

Embrace Diverse Expertise
